| ACLs (required windows) | passed unconditionally | passed unconditionally | ✅ MATCH |
| Stack outputs → proto | `table_id` = `ResourceManagerId` attribute | `table_id` = `resource_manager_id` attribute | ✅ MATCH (byte-identical) |
| Azure tags | none (ARM: unsupported on tables) | none | ✅ MATCH |

**The exception, in full:** pulumi-azure v6 has not bridged the table's
`storage_account_id` input — verified against the PINNED v6.38 via
`go doc .../storage.TableArgs` AND confirmed v6.38 is the LATEST v6
(`go list -m -versions`), so no SDK bump closes it. The spec keeps the ARM-id parent
(the catalog grain); each engine addresses the provider its own way; the created table
is identical; `table_id` deliberately carries the `resource_manager_id` attribute on
BOTH engines so outputs never see the difference. `PARITY-EXCEPTION:` comments in
`iac/tf/main.tf` and `iac/pulumi/module/main.go` record the re-alignment trigger
(a bridge release carrying `storageAccountId` on `storage.Table`).

Verified with `planton validate-outputs` (schema check) and the
`pkg/outputs/conformance_test.go` case for AzureStorageTable (PASS, 3/3 fields).

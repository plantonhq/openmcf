# Azure ExpressRoute Gateway -- Operational Guide

Judgment that does not fit in field references.

## It bills from creation, before any circuit is connected

Each scale unit bills hourly, around the clock, the moment ARM accepts
the create -- whether or not a single connection exists. Create the
gateway when a circuit is genuinely imminent, not when the hub is.
Deleting and recreating later costs only the provisioning time
(measured live: create ~27 minutes, delete ~13). Verified figures live
in the generated estimate at
`catalog/_pricing/estimates/azureexpressroutegateway.yaml`, computed
from the pinned, source-dated price book.

## Scale units are a floor, not a size

ARM auto-scales ABOVE `scaleUnits` under load and bills for what runs;
the setting is the guaranteed (and minimum-billed) capacity. Start at
1 unless the circuit's committed bandwidth already exceeds ~2 Gbps --
raising the floor later is an in-place update.

## Connections need a PROVISIONED circuit

ARM accepts a connection only when the circuit's provider side is
provisioned -- a live carrier cross-connect or an ExpressRoute Direct
port behind it. Against an unprovisioned circuit the create fails on
the circuit's provisioning state; that is a prerequisite problem, not
a module defect. Sequence real deployments: circuit ordered → carrier
provisions → THEN the connection.

## Cross-subscription keys are single-purpose secrets

An `authorizationKey` is generated by the circuit owner's authorization
and redeemable ONCE. Treat it like a password in transit (it is marked
sensitive throughout), and expect an imported connection to plan an
in-place update on it -- ARM never returns the key on reads.

## One gateway per hub, deletion before the hub

A hub holds at most one ExpressRoute gateway, so a second create in
the same hub fails on ARM's side. And like everything in the Virtual
WAN family, deletion is bottom-up: connections → gateway → hub.

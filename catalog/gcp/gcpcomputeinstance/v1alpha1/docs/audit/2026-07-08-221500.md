## Spec depth vs the released provider floor

Modeled at the released `google ~> 6.0` floor of
`google_compute_instance` (schema-probe verified against the pinned
6.50.0): ambient `project_id` (→ GcpProject), `instance_name` with the
metadata.name fallback (explicit conditional on both engines), zone,
machine type, description, custom FQDN `hostname`; the boot disk with
the exactly-one-source contract (image XOR `source_snapshot` XOR
`source_disk` → GcpComputeDisk, CEL-enforced) plus CMEK → GcpKmsKey,
disk labels, hyperdisk provisioned IOPS/throughput, architecture,
confidential-mode disk, boot-disk resource policies, and storage pool;
`attached_disks[]` as first-class GcpComputeDisk references
(`status.outputs.self_link`) with mode + per-attachment CMEK; local-SSD
`scratch_disks[]` (NVME/SCSI, 375/3000 GB); NIC depth — network +
subnetwork FKs, Shared-VPC `subnetwork_project`, static internal
`network_ip` → GcpAddress, external `access_configs[].nat_ip` →
GcpAddress + network tier + public PTR, IPv6 access configs,
`stack_type`, `nic_type` (GVNIC/VIRTIO_NET/IDPF/MRDMA/IRDMA),
`queue_count`, alias IP ranges; service account (email → GcpServiceAccount
+ scopes); consolidated scheduling — single `provisioning_model` Spot
switch (both engines derive the API's legacy preemptible flag;
automatic restart forced off; CEL-guarded), maintenance behavior,
termination action, `max_run_duration_seconds` XOR `termination_time`
(CEL), on-stop local-SSD discard, availability domain, sole-tenant
`node_affinities` + `min_node_cpus`, local-SSD recovery timeout;
shielded VM (secure boot / vTPM / integrity monitoring with GCP-default
semantics); confidential VM (`SEV`/`SEV_SNP`/`TDX`, TERMINATE-maintenance
CEL); advanced machine features (nested virt, SMT control, visible
cores, UEFI networking, PMU, turbo mode); `guest_accelerators[]`
(TERMINATE-maintenance CEL); reservation affinity (specific-reservation
coherence CEL); TIER_1 egress bandwidth; metadata + dedicated
`startup_script`; `ssh_keys` folded to the metadata `ssh-keys` key
byte-identically on both engines; user labels merged beneath
`planton-ai_*` attribution labels; network tags; Resource Manager tags;
instance resource policies (max 1); `min_cpu_platform`;
`can_ip_forward`; `enable_display`; honest default-false
`deletion_protection` (the data levers are the disks);
`desired_status` (RUNNING/SUSPENDED/TERMINATED stop/start lever);
`allow_stopping_for_update`; `key_revocation_action_type`.

**Recorded skips (docs/README.md):** dynamic-NIC fields (`igmp_query`,
`vlan`, `parent_nic_name` — absent from released 6.50.0, probe-verified),
`partner_metadata` + `scheduling.graceful_shutdown` (beta-only), raw
CSEK keys (secret material in manifests/state; CMEK is the modeled
path), `network_attachment` PSC interfaces (future first-class kind),
legacy preemptible-without-Spot.

## Cross-Engine Parity (--parity)

**PARITY ✅** — both engines implement the identical contract:

- The tfvars converter contract (plain resolved strings) on TF; typed
  `GetValue()` reads on Pulumi.
- Label semantics unified: user labels first, `planton-ai_*` attribution
  labels win on conflicts — the TF module's legacy label keys AND its
  user-labels-last merge order are both closed; the E2E verifier asserts
  the attribution label live.
- `ssh_keys` fold, Spot derivation (preemptible + automatic-restart),
  shielded defaults, and the metadata/startup-script split are
  byte-identical by construction.
- Outputs are name-identical across engines, including the previously
  Pulumi-missing `status` export and the empty-string `external_ip`
  contract for private VMs (struct-based apply; TF `try()`).
- `google ~> 6.0` on TF (hardcoded 6.19.0 pin removed); every modeled
  field bridge-verified against pulumi-gcp v9.
- API enablement (`compute.googleapis.com`) on both engines.

**Zero PARITY-EXCEPTIONs.**

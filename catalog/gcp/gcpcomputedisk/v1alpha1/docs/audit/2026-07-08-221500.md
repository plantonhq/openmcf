## Spec depth vs the released provider floor

Modeled at the released `google ~> 6.0` floor of `google_compute_disk`
(schema-probe verified against the pinned 6.50.0): ambient `project_id`
(→ GcpProject), `disk_name` with the metadata.name fallback, zone,
description, the full disk-type surface (pd-standard/balanced/ssd/
extreme + the hyperdisk family), `size_gb` with grow-only semantics
taught, the at-most-one-source contract (image XOR `source_snapshot`
XOR self-kind `source_disk` clone; empty disk requires `size_gb` —
both CEL-enforced), CMEK → GcpKmsKey (confidential-compute-requires-CMEK
CEL), hyperdisk `provisioned_iops`/`provisioned_throughput`,
`access_mode` (READ_WRITE_SINGLE / READ_WRITE_MANY / READ_ONLY_MANY),
architecture, confidential-compute mode, physical block size
(4096/16384), `create_snapshot_before_destroy` + custom prefix (the
last-resort recovery net), storage pool, user labels merged beneath
`planton-ai_*` attribution labels, and Resource Manager tags.

Outputs export the attachment composition keys: `name`, `disk_id`,
`self_link` (what `GcpComputeInstance.attached_disks[].source` and
`boot_disk.source_disk` consume), plain-name `zone`, `size_gb`, and
`type` normalized to the last path segment on BOTH engines (the
bridged-attribute-format parity class applied at forge time).

**Recorded skips (docs/README.md):** regional dual-zone disks (a
separate provider resource with a materially different surface — fails
the dual-scope fold test; future kind), raw CSEK keys (secret material
in manifests/state), async primary-disk replication pairs (depends on
the regional kind), `guest_os_features`/`licenses` (image-derived),
`source_instant_snapshot` + `source_storage_object` import arms
(specialist migration paths).

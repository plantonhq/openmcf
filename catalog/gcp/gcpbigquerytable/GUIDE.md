# GcpBigQueryTable Guide

The judgment this guide protects: a table is where the data actually
lives — most fields here are recoverable configuration, but schema,
partitioning, and the destroy levers guard the unrecoverable part.

## One table, one arm

A table is native (schema), a logical view (query), a materialized view
(query + refresh), or external (data stays in GCS/Sheets/Bigtable) —
the spec enforces at most one arm. Resist "a view would be easier here"
drift: views inherit their base tables' permissions model through
authorized views on the DATASET, and that is where sharing decisions
belong.

## Two destroy levers, and ABANDON is the bypass

`deletionPolicy` is checked FIRST: `PREVENT` fails the destroy before
anything else is consulted, and `ABANDON` drops the table from
management without touching data — bypassing `deletionProtection`
entirely. Only `DELETE` (the default) proceeds to the second lever,
where `deletionProtection: true` (the default) still refuses. So:
destroying a table's data requires BOTH `deletionPolicy: DELETE` (or
unset) AND `deletionProtection: false` — two explicit decisions, by
design.

## Partitioning is a create-time decision

Time vs range partitioning (mutually exclusive) and the partition
column cannot be changed on a populated table without recreating it —
which with real data means a copy job and a cutover. Decide by query
shape: partition on the column every query filters by, cluster on the
next three.

## The schema-diff knobs hide drift — use them for their one job

`ignoreAutoGeneratedSchema` stops fights over columns BigQuery itself
adds; `ignoreSchemaChanges: ["dataPolicies"]` stops fights over
column-level data-policy attachments managed by governance tooling.
Both make the spec's schema less authoritative — turn them on when the
named external writer exists, not preemptively.

## External tables: the data is not yours to destroy

An external table's destroy removes METADATA only — the GCS objects (or
Bigtable/Sheets source) live on, owned by their own kind. Decimal
conversions (`decimalTargetTypes`) follow the API's fixed
NUMERIC → BIGNUMERIC → STRING precedence regardless of list order, and
CSV `sourceColumnMatch: NAME` trades position-stability for
header-dependence — the right choice only when upstream reorders
columns.

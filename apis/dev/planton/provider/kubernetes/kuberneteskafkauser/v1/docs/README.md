# KubernetesKafkaUser: Research and Design

## Introduction

A KafkaUser is the Strimzi custom resource that declares one Kafka
client identity: how it authenticates, what it may do, and how hard it
may push the brokers. This component creates one KafkaUser, named after
the resource (`metadata.name`). The credentials are generated by the
cluster's USER OPERATOR, not by the IaC modules — the declaration is
public shape, the credential is operator-born.

## The Upstream Model

Strimzi's user operator runs per cluster (part of the entity operators
a KubernetesKafka deploys by default). When a KafkaUser with `tls` or
`scram-sha-512` authentication is created, the operator creates the
principal in Kafka and generates a Kubernetes Secret WITH THE SAME NAME
AS THE USER carrying the credentials. It also manages the user's ACLs
(through the Kafka Admin API) and quotas. `kubectl apply` and
`kubectl delete` on the resource create, modify, and delete the real
principal.

## The Placement Contract

The user operator watches a SINGLE namespace — the Kafka cluster's own
— and selects resources by the `strimzi.io/cluster` label. A KafkaUser
in any other namespace, or labeled for a cluster that does not exist
there, is accepted by the API server and then silently never reconciled.
The spec therefore requires `namespace` (which MUST be the cluster's
namespace) and `kafka_cluster` (rendered as the label); the modules
stamp the label unconditionally.

## Authentication: Three Types, Two Secrets, One Rule

The one rule: the user's authentication type must match the equivalent
listener configuration on the target cluster. A scram-sha-512 user
cannot authenticate on a tls-auth listener and vice versa.

- **`scram-sha-512`** — the operator generates a password into the
  user's Secret: a `password` key plus a ready-made `sasl.jaas.config`
  key (the JAAS string SASL clients consume directly). Pairs with
  scram-sha-512 listeners.
- **`tls`** — the operator issues a client certificate from the
  cluster's clients CA into the user's Secret: `user.crt` / `user.key`
  in PEM form plus `user.p12` / `user.password` PKCS #12 keystore
  forms (and `ca.crt`, the clients CA that signed it). Certificates
  renew with the clients CA. Pairs with tls-auth listeners; the
  principal is `CN=<user-name>`.
- **`tls-external`** — mutual TLS with certificates issued OUTSIDE the
  cluster. NO Secret is generated; the user exists so ACLs and quotas
  can be managed for the externally-issued principal (`CN=<name>`
  form).

Omitting `authentication` entirely is the ACL-only principal form: no
credentials are generated (upstream: the operator does not create
credentials without a type), and the ACLs apply to an identity
authenticated by other means — custom listener mechanisms.

## Authorization: Simple ACLs, Enforced Only When the Cluster Plays

`authorization.type` is `simple` — Strimzi's only type, Kafka's
built-in ACL model managed through the Admin API. Each rule names a
resource (`topic`, `group`, `cluster`, `transactionalId`; `literal` or
`prefix` matching — only cluster ACLs are nameless), the operations
granted (Read, Write, Create, Delete, Alter, Describe, ClusterAction,
AlterConfigs, DescribeConfigs, IdempotentWrite, All), and an optional
host restriction (empty = any host).

The enforcement dependency is the sharp edge: ACLs are effective only
when the CLUSTER runs `simple` authorization. Declaring ACLs against a
cluster without it makes the user NotReady (the operator rejects the
rules as unsupported by the cluster configuration); a cluster without
authorization enforces nothing — every authenticated client can do
everything. The canonical grants, from the upstream examples: a
producer needs Write + Describe (+ Create if it may create the topic,
+ IdempotentWrite for idempotent producers); a consumer needs Read +
Describe on the topic and Read on its consumer group.

## Quotas

Broker-enforced client caps, all modeled: `producer_byte_rate` and
`consumer_byte_rate` (bytes/second before throttling, per broker),
`request_percentage` (share of broker request-handler time), and
`controller_mutation_rate` (partition create/delete mutations per
second). Quotas apply to the principal regardless of authorization
mode.

## Deliberately Unmodeled

Stated timelessly, for the record — against the KafkaUser CRD surface:

- **`template.secret`** — upstream lets a KafkaUser stamp extra labels
  and annotations onto the generated Secret. Unmodeled: the Secret is
  operator-owned machinery, and the platform's consumers locate it
  through the `secret_name` output, not through metadata conventions.
- **`authentication.password`** — bring-your-own SCRAM password via a
  Secret reference. Unmodeled: operator-generated passwords are the
  point of the kind; a hand-managed password reintroduces the secret
  material this kind exists to keep out of manifests.
- **`authentication.validityDays` / `renewalDays`** — per-user tls
  certificate lifetime overrides. Unmodeled: certificate lifetime
  policy belongs to the cluster's clients CA (the default when these
  are absent), not to individual users.
- **ACL `type: deny`** — upstream rules can be allow OR deny. Only
  allow-rules are modeled: deny-lists interleaved with allow-lists are
  a notorious source of authorization surprises, and the platform's
  grant model is additive.
- Any of these is expressible via KubernetesManifest without leaving
  the platform.

## Engine Mechanics

- **Pulumi**: one untyped CustomResource (`kafka.strimzi.io/v1`
  KafkaUser) — no generated package is shipped for the Kafka family
  (crd2pulumi cannot carry the family CRDs' free-typed config objects;
  the same ruling as the KubernetesKafka module).
- **Terraform**: one `kubectl_manifest` (alekc/kubectl) — no cluster
  connection at plan time, so users plan before the Strimzi CRDs exist
  (single-run infra charts, offline plan proofs). The locals render the
  same shape as the Pulumi module; twins kept in lockstep.
- **No namespace resource, deliberately**: the namespace belongs to the
  KubernetesKafka resource's lifecycle — this kind only places into it.
- **No secret material, structurally**: the module renders
  authentication TYPE, ACLs, and quotas — never credentials. Nothing in
  the state is sensitive.
- **No await machinery**: reconciliation belongs to the user operator,
  not to applying the resource. `kubectl get kafkauser` shows Ready /
  NotReady with a teaching message.

## The secret_name Output

Both engines export `secret_name` with the same honest conditional:
equal to the user name for credential-bearing users, EMPTY for
`tls-external` and authentication-less users (no Secret is generated
for either). Workloads mount or env-reference the Secret exactly as
they would a KubernetesSecret; the `username` output carries the
principal name for super-user lists and externally-managed ACL tooling.

## Validation Highlights

Vocabulary checks with teaching messages: authentication type
(scram-sha-512 / tls / tls-external), authorization type (simple only),
per-rule operations (the eleven-verb enum), resource types (topic /
group / cluster / transactionalId), pattern types (literal / prefix), a
name-required-unless-cluster rule on ACL resources, at-least-one-ACL on
the authorization block, and non-negative quota values.

## E2E

The kind-cluster lane deploys a Kafka fixture with a scram-sha-512
listener and simple authorization, then proves the loop on the wire:
the behavioral scenario reads the operator-generated SCRAM credential
from the user's Secret, produces to the topic its first ACL allows, and
consumes under the group its group ACL allows — authentication AND ACL
authorization exercised as a real client.

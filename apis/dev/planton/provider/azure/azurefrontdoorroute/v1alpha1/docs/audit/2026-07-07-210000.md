## Addendum (2026-07-08): rule-set and custom-domain references landed

The two deferred reference seams shipped with their kinds
(`AzureFrontDoorRuleSet` 485, `AzureFrontDoorCustomDomain` 486):

- Spec gains `rule_set_ids` (beside the origin references) and
  `custom_domain_ids` (beside `link_to_default_domain`), both repeated
  `StringValueOrRef` with default-kind wiring; fields renumbered
  contiguously.
- The previously-documented apply-time contract is now the
  `front_door_route_default_domain_or_custom_domains` message CEL
  (disabling the default domain requires >= 1 custom domain) --
  azurerm's exact create/update rule, no longer deferred; spec tests
  cover both paths.
- Both modules send the two collections only when populated (Front
  Door's empty-means-disassociate quirk normalized identically); the
  hack manifest and `planton tofu plan` exercise both seams plus the
  disabled default domain.
- The `custom_domain_association` verdict is unchanged and now fully
  realized: no cycle exists across decomposed kinds, so the route's
  own field IS the attachment -- no association construct in either
  module, no kind.
- New E2E scenario `rule-set-attach.yaml` (the composed chain plus a
  scenario-declared rule-set fixture) live-proves the rule_set_ids
  seam; the custom-domain attach seam requires a VALIDATED domain and
  carries the recorded exclusion in the custom-domain kind's profile.
- Parity re-verified across the new dimensions; `pkg/outputs`
  unchanged (no new outputs). **PARITY ✅ COVERAGE ✅ stand.**

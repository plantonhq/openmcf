`pkg/outputs/conformance_test.go` case passes
(`TestStackOutputsConformance/AzureStorageContainer`).

| Cloud object naming | `spec.container_name` | `var.spec.container_name` | ✅ MATCH |

**Legend:** ✅ MATCH | ⚠️ DIVERGES (undocumented) | 🔵 EXCEPTION (documented `PARITY-EXCEPTION:`)

✅ **In parity:**

- **Every `spec.proto` field is honored by both engines** — all six fields
  (`storage_account_id`, `container_name`, `container_access_type`,
  `default_encryption_scope`, `encryption_scope_override_enabled`,
  `metadata`) verified field-by-field above. No field is implemented on
  one side and ignored on the other.
- **The enum vocabulary is exhaustive and identical**: three members on
  each side, same azurerm lowercase wire values, and the unset case
  materializes `"private"` identically — a container is born locked down
  on either engine.
- **The encryption-scope pair is empty-vs-omitted-safe on both sides**:
  azurerm's `default_encryption_scope` is Computed+ForceNew, so sending
  `""` would diff/replace; both engines omit it when unset, and the
  override flag is presence-guarded on both.
- **Stack outputs are name-identical in triplicate**: every key in
  `outputs.go` (`container_id`, `container_name`, `storage_account_name`)
  has a same-named output in `outputs.tf` and a same-named field in
  `stack_outputs.proto`. The generic reflection transformer maps all three
  by name on both engines (dry-run verified).

⚠️ **Edge-case observation (not outcome-changing, recorded as Defect 2):**

- **Malformed-ARM-id failure layer differs.** Terraform's end-anchored
  regex fails the plan for ANY id that doesn't end in
  `/storageAccounts/<name>`. Pulumi's guard (`last segment non-empty` +
  `contains "/storageAccounts/"`) accepts an id with trailing segments
  after the account name (e.g. `.../storageAccounts/acct/blobServices`),
  computes the wrong name, and only fails when the azurerm provider
  rejects the malformed `storage_account_id` at apply. For every id Azure
  would actually accept — including everything the
  `AzureStorageAccount.storage_account_id` FK can resolve to — both
  engines produce the identical result; on the malformed class both
  engines fail before any output persists. Deployed outcomes never
  diverge, so this does not trip the parity gate, but the Pulumi guard is
  weaker than the module README's "loud error if the id is not a
  storage-account ARM id" claim.

**Effect on score:** none — no undocumented outcome-changing divergence;
Categories 4 and 5 are not capped.

### Protobuf API Definitions — validation quality note

The spec stands at the released 6.50.0 floor (GA == beta at the pinned tag,
diff-verified): ambient-optional `project_id` ref, immutable `location`,
mutable `display_name`/`description`/`labels`, immutable
`index_update_method` (BATCH_UPDATE default vs STREAM_UPDATE, both regimes
taught in the message comment), `contents_delta_uri` +
`is_complete_overwrite`, and the required, fully immutable `config` block
(required `dimensions`, `approximate_neighbors_count`, `shard_size`,
`distance_measure_type`, `feature_norm_type`, tree-AH XOR brute-force
algorithm arms). Two message-level CEL rules encode what the provider does
NOT enforce client-side: `at_most_one_algorithm` (the provider's
`ExactlyOneOf` lists are EMPTY at the pinned tag — verified against the
installed schema) and `tree_ah_requires_neighbors_count` (the API's
runtime-only create rejection, moved pre-deploy). Every enum-string field
carries a value-list CEL with a complete user-facing message. 43-case spec
test, all green, covering every CEL rule positive + negative and the
boundary values.

### The two provider quirks — taught, not patched around

`contents_delta_uri` is write-only (GET never returns it) and a change to
it travels in its OWN single-field PATCH. Both quirks are documented on
the spec field, in `docs/README.md`, and in matching module comments on
both engines, so an out-of-band data load producing a one-field diff on
the next plan is expected behavior, not a surprise. The `metadata` block
is deliberately flattened into the spec (design decision #2 in
`docs/README.md`) — the provider's `metadata` wrapper is an API packaging
artifact that would collide conceptually with KRM `metadata`.

### Cross-Engine IaC Parity (Critical GATE)

**Parity verdict: PARITY ✅**

- Both engines enable `aiplatform.googleapis.com`
  (`disable_on_destroy=false`) and gate the index on it.
- Identical labels merge: user labels first, `planton-ai_*` attribution
  set wins on conflict; key set verified identical (Pulumi's
  `gcplabelkeys.WithNormalizedDomainPrefix` emits exactly the strings the
  TF locals hardcode).
- `region` pinned to `location` on both engines (the 671 sibling's
  live-discovered lesson applied from the start).
- Every optional scalar (`description`, `index_update_method`,
  `shard_size`, `distance_measure_type`, `feature_norm_type`,
  `approximate_neighbors_count`, tree-AH leaf knobs) is send-only-when-set
  on BOTH engines so GCP's own defaults apply identically.
- `is_complete_overwrite` is gated on `contents_delta_uri` presence and
  sent even when `false` in that case — identical conditionals both sides.
- Bridged-provider `deletion_policy` (7.x client-side; absent from the
  released 6.50.0 GA schema) pinned to `DELETE` on Pulumi with a PARITY
  comment.
- Outputs identical keys and value sources on both engines: `index_id`
  (full resource path — the deployed index's composition key),
  `index_name` (numeric), `metadata_schema_uri`, `create_time`,
  `update_time`.

### Composition contract

`index_id` (the fully qualified path) is exactly the value
`GcpVertexAiDeployedIndex.spec.index` consumes via `default_kind` FK
wiring. `contents_delta_uri` stays a plain documented string (a `gs://`
DIRECTORY URI with no matching stack-output shape on the GCS kinds — the
sibling endpoint's `bigquery_destination_uri` precedent).

### Recorded skips (with reasons)

- `encryption_spec` (CMEK) — not in the released 6.x `google` line for
  this resource (7.x-only); catalog floats `~> 6.0`. Revisit at the
  catalog-wide major bump.
- `deployed_indexes` output — volatile operational state (entries
  appear/disappear as deployments come and go); the relationship is
  modeled first-class by GcpVertexAiDeployedIndex.
- `index_stats` output — volatile data-plane state (vector/shard counts
  change with every upsert).
- `etag` output — optimistic-concurrency plumbing, not a composition key.
- Batch-load live E2E (a populated `contents_delta_uri` index) — a real
  corpus build runs tens of minutes to hours (provider timeout 180m);
  the batch arm is proven offline (spec CEL + converter plan + preset
  validation) per RoE §18, with the empty-index live run covering the
  create/destroy lifecycle on both engines.

## Spec depth vs the released provider floor

Modeled at the released `google ~> 6.0` floor of
`google_artifact_registry_repository`: `repository_id` (metadata.name
fallback), `location`, ambient `project_id`, free-string `format`
(staleness-trap-free; API validates), `mode` with the four mode↔config
coherence CEL rules, `description`, user `labels`, CMEK → GcpKmsKey FK,
`docker_config.immutable_tags`, `maven_config` (version policy +
snapshot overwrites), `cleanup_policies` (DELETE/KEEP with condition +
most_recent_versions and two KEEP-coherence CEL rules) +
`cleanup_policy_dry_run`, `remote_repository_config` (all seven upstream
arms under an exactly-one CEL; upstream credentials as a Secret Manager
version REFERENCE — no secret material in spec or state),
`virtual_repository_config.upstream_policies` (self-kind FK →
`repository_path`), `vulnerability_scanning_enablement`, and additive
`iam_members` (role + member ref → GcpServiceAccount `member` output +
optional IAM condition).

**Recorded skips (docs/README.md):** repository-level IAM
binding/policy trio (authoritative clobber semantics — the catalog
models additive grants only), `google_artifact_registry_rule` +
`google_artifact_registry_project_config` (Tier-2 kinds),
`google_artifact_registry_vpcsc_config` (beta-only resource),
`deletion_policy` spec field (client-side virtual flag; pinned DELETE in
the Pulumi module with a PARITY comment instead).

**Contract rework (approved):** the bundled reader/writer service
accounts + exported SA keys were removed — SA key material in state
contradicted the keyless-first catalog; `GcpServiceAccount` +
`GcpProjectIamMember` + inline additive `iam_members` are the composable
replacements. Zero inbound FKs referenced the old outputs (verified
repo-wide); the new outputs are `name`, `repository_path`,
`registry_uri`, `location`.

## Detailed Findings

### Protobuf API Definitions — validation quality note

The spec models one additive IAM grant: `roles/iam.workloadIdentityUser` on a
GSA to the constructed principal
`serviceAccount:{pool-project}.svc.id.goog[{ksa-namespace}/{ksa-name}]`.
Fields: ambient-optional `project_id` ref (pool project), required
`service_account_email` ref, RFC-1123-validated `ksa_namespace` and `ksa_name`,
and optional IAM `condition` (title/expression/description). All fields are
immutable — an IAM grant has no update path. The KSA annotation
(`iam.gke.io/gcp-service-account`) is deliberately out of scope (Kubernetes
side). 15-case spec test.

**Session deliverables:** rebuilt spec and dual-engine modules
(`workload_identity_binding.go` / TF `main.tf`); principal derived identically
from validated parts on both engines; `gke_workload_identity_binding.go`
verifier probing the GSA IAM policy for the exact (role, member) pair; E2E
`minimal` scenario chained to `GcpServiceAccount` prerequisite; one standard
preset.

### Cross-Engine IaC Parity (Critical GATE)

**Parity verdict: PARITY ✅**

- Both engines create `google_service_account_iam_member` with role
  `roles/iam.workloadIdentityUser` and the same constructed member string.
- `project_id` omission falls back to provider default on both engines.
- Optional IAM condition maps to identical `condition` blocks (title,
  expression, description).
- Outputs export `member`, `service_account_email`, `role`, and
  `project_id` with matching semantics — the verifier reads `member` +
  `service_account_email` to probe existence.

### Composition contract

Prerequisite: `GcpServiceAccount`. Leaf IAM grant — merges additively into
the GSA policy without touching other principals. The `service_account_email`
output is the value the workload's KSA annotation needs. Pairs naturally with
cert-manager / Cloud DNS solver patterns documented in the README.

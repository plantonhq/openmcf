## Spec depth vs the released provider floor

Modeled at the released `google ~> 6.0` floor of
`google_filestore_instance` (schema-probe verified against the pinned
6.50.0): ambient `project_id` (→ GcpProject, conformed from the old
required contract), `instance_name` with the metadata.name fallback
(conformed from required-explicit — no reservation-window reason
exists), zone-or-region `location`, the full 8-value `tier` surface,
description, `protocol` (NFS_V3/NFS_V4_1), CMEK → GcpKmsKey, the
deletion-protection pair, the single file share (name, grow-only
capacity, ≤10 NFS export options with access/squash/anon controls, and
the `source_backup` restore arm), the single VPC attachment — network →
GcpVpcNetwork resolved to the **plain network name** (the Filestore API
rejects self-link URLs; the FK's `default_kind_field_path` targets
`status.outputs.network_name`, found live and fixed), connect mode
(DIRECT_PEERING / PRIVATE_SERVICE_ACCESS / PRIVATE_SERVICE_CONNECT —
the released enum), reserved /29 range, and `modes` (IPv4/IPv6, default
MODE_IPV4 — previously hardcoded), IOPS `performance_config`
(fixed XOR per-TB, CEL), `initial_replication` (ACTIVE/STANDBY with
peers as self-kind GcpFilestoreInstance references via
`status.outputs.instance_id`), user `labels` (a wholly new surface —
the spec previously had none), and Resource Manager `tags`.

Outputs extended extend-only with the GCP-resolved `reserved_ip_range`
and the concurrency `etag`.

**Recorded skips (docs/README.md, all probe-verified absent from
released 6.50.0):** `psc_config.endpoint_project`,
`nfs_export_options.network`, LDAP `directory_services`,
`source_backupdr_backup`, `deletion_policy` (the bridged provider's
client-side flag is pinned to DELETE with a PARITY comment instead).
Filestore backup/snapshot kinds deliberately deferred (one-shot
point-in-time lifecycle fits continuously-reconciled IaC poorly; GCP
has no Filestore schedule resource; revisit on pull).

## Detailed Findings

### 1–2. Registry and Structure

✅ Enum 643 (data sub-band); `prerequisites: [GcpFirestoreDatabase]`;
full anatomy including `e2e/` (minimal scenario on the database
prerequisite chain, with a consumer-unique prerequisite database name —
Firestore holds deleted database IDs for minutes, so sibling chains in
one run must not share one).

### 3. Protobuf API Definitions

✅ The managed-backup protection node, many-per-database with the
daily-plus-weekly pattern expressible as two resources: `database` ref →
the database's `database_name` output, `retention` (seconds string,
≤ 14 weeks — the only mutable field), `daily` XOR `weekly_recurrence.day`
under an exactly-one CEL. Backups-outlive-the-schedule semantics taught
in spec and docs (deleting the schedule stops future backups, never
deletes existing ones). 17-case spec test green.

### 4–5. IaC Modules

✅ Both engines: Firestore API enablement; exactly-one recurrence
translated identically (empty daily marker block vs weekly day);
`schedule_id` derived from the server-assigned name's last path segment
on both engines. Canonical Pulumi.yaml; `~> 6.0`.

### 5b. Cross-Engine IaC Parity (GATE)

**PARITY ✅** — project source, recurrence translation, retention
passthrough, dependency ordering, and both output keys
(`schedule_id`, `database`) identical. `validate-outputs` green both
module dirs; conformance case green.

### 6–11. Documentation, Presets, Coverage

✅ Docs position the schedule against PITR (7-day version history vs
14-week backups that survive database deletion) and teach the
two-schedule daily+weekly composition. 2 preset pairs
(daily-short-retention / weekly-long-retention) validate; site catalog
page created (`firestore-backup-schedule/`). No secrets — coverage gate
green.
